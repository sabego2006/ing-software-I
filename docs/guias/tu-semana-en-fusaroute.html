Una sola vez · antes del martes 15

Montar tu ambiente

Tarda una tarde. Hazlo antes del Sprint 1, no el día que necesites programar.

«Ambiente» aquí significa: todo lo que tiene que estar instalado y prendido en tu portátil para que el proyecto corra. El nuestro se llama DEV y es tuyo: la base de datos vive en tu máquina, con tus datos de prueba. Si la rompes, no rompes nada de nadie. Esa es exactamente la gracia.

Lo que hay que instalar

ProgramaVersiónPara qué
Gitla últimabajar y subir código
JDK Temurin25correr el backend (Java)
Apache Maven3.9+compilar el backend
PostgreSQL16 o 17la base de datos
Node.js22 LTScorrer el frontend (Angular)

La forma más corta en Windows es con winget, que ya viene instalado. Abre PowerShell y pega esto línea por línea:

winget install --id Git.Git
winget install --id EclipseAdoptium.Temurin.25.JDK
winget install --id Apache.Maven
winget install --id PostgreSQL.PostgreSQL.17
winget install --id OpenJS.NodeJS.LTS
Ojo con esto

Cierra PowerShell y ábrelo de nuevo cuando termine de instalar. Si no, tu terminal no se entera de los programas nuevos y todo lo de abajo te va a decir «no se reconoce el comando». Es la causa número uno de que este paso «no funcione».

Cuando el instalador de PostgreSQL te pida una contraseña para el usuario postgres, anótala. La vas a necesitar en el paso 4 y no hay forma fácil de recuperarla.

Para comprobar que todo quedó, pega esto. Deben salir cinco versiones y ningún error:

git --version
java -version      # tiene que decir 25
mvn -version
node --version
psql --version

Los pasos

  1. Crea la carpeta de trabajo y clona los tres repos

    Los dos repos de código son hermanos dentro de la misma carpeta, y el de la asignatura va aparte porque es donde viven los entregables.

    mkdir C:\dev\FusaRoute
cd C:\dev\FusaRoute
git clone https://github.com/sabego2006/FusaRoute-BACKEND.git
git clone https://github.com/sabego2006/FusaRoute-FRONTEND.git
git clone https://github.com/sabego2006/ing-software-I.git

    Si Git te pide usuario y contraseña, dile que sí a abrir el navegador e inicia sesión con tu cuenta de GitHub. Con eso queda guardado y no vuelve a preguntar.

  2. Crea la base de datos y tu propio usuario

    Entra a psql con el superusuario que acabas de crear. Te va a pedir la contraseña de postgres que anotaste, de forma interactiva — escríbela ahí, nunca la pegues en un comando ni se la muestres a nadie por chat.

    psql -U postgres

    Si te responde psql: command not found, es que el instalador no lo dejó en el PATH. Usa la ruta completa:

    & "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres
    Regla fija: la app nunca usa postgres

    postgres es el superusuario — puede borrar cualquier base del servidor. La aplicación se conecta siempre con un usuario propio, dueño solo de su base. Si ese usuario dedicado se filtra algún día, el daño se queda en una base vacía de pruebas; si se filtra el superusuario, se pierde todo el servidor. Ya adentro de psql, pega esto completo — cambia TU_CONTRASEÑA_AQUI por una que uses solo para esto:

    CREATE DATABASE fusaroute_dev;
CREATE USER fusaroute_dev WITH PASSWORD 'TU_CONTRASEÑA_AQUI';
GRANT ALL PRIVILEGES ON DATABASE fusaroute_dev TO fusaroute_dev;
\c fusaroute_dev
GRANT ALL ON SCHEMA public TO fusaroute_dev;
\q

    Anota esa contraseña nueva — es la que va en tu .env en el paso siguiente, no la de postgres.

  3. Crea tu .env del backend

    Cada repo trae un .env.example: es la lista de las variables que existen, con los valores vacíos. Tú haces tu copia y la llenas. Tu .env nunca se sube a GitHub — ya está bloqueado en .gitignore, no tienes que hacer nada para que eso pase.

    cd C:\dev\FusaRoute\FusaRoute-BACKEND
Copy-Item .env.example .env
notepad .env

    Llénalo así, con el usuario y la contraseña de fusaroute_dev que creaste en el paso anterior — no con postgres:

    SPRING_PROFILE=dev
PORT=8080
DB_URL=jdbc:postgresql://localhost:5432/fusaroute_dev
DB_USERNAME=fusaroute_dev
DB_PASSWORD=la contraseña que le pusiste a fusaroute_dev
GOOGLE_MAPS_API_KEY=
JWT_SECRET=cualquier texto largo por ahora

    Las dos últimas pueden quedar vacías hasta que existan las historias que las usan.

  4. Arranca el backend

    Windows no lee el .env solo, hay que cargárselo. Esta línea larga hace eso; pégala completa:

    cd C:\dev\FusaRoute\FusaRoute-BACKEND
Get-Content .env | ForEach-Object { if ($_ -match '^\s*([^#][^=]*)=(.*)$') { [Environment]::SetEnvironmentVariable($matches[1].Trim(), $matches[2].Trim()) } }
mvn spring-boot:run
    Se carga por ventana

    Esa línea vale solo para la ventana de PowerShell en la que la pegaste. Si cierras la terminal, hay que volver a pegarla antes de arrancar. No es un error tuyo: es cómo funciona.

    La primera vez se demora, porque Maven baja medio internet. Cuando veas Started FusaRouteApplication, abre otra ventana de PowerShell y comprueba:

    curl http://localhost:8080/health

    Tiene que responder {"status":"UP"}. Ese es el momento en que tu ambiente DEV existe.

  5. Arranca el frontend

    En una tercera ventana, dejando el backend corriendo:

    cd C:\dev\FusaRoute\FusaRoute-FRONTEND
Copy-Item .env.example .env
npm ci
npm start

    Abre http://localhost:4200. Debe cargar la página de Angular.

    npm ci es el que instala las dependencias. Se demora varios minutos la primera vez y no hay que volver a correrlo salvo que alguien cambie package.json.

Nunca, en ningún caso

No subas el archivo .env, ni pegues una contraseña o una llave dentro de un archivo .properties o .ts. Si una credencial entra a GitHub, queda en el historial para siempre aunque después la borres, y toca cambiarla en el proveedor. Ante la duda, pregunta antes de subir.

Martes · 18:00, saliendo de clase

Planning

Una hora. Abre el sprint de la semana. Tú lo diriges: eres la Product Owner.

Ser PO no es «la que reparte tareas». Es la que decide qué se construye primero y qué significa que esté bien hecho. Santiago decide el cómo técnico; tú decides el qué y el para quién. Cuando el comité pregunte por qué se hizo primero el login y no el mapa, la que responde eres tú.

Las tres cosas que dices

01 «Este sprint vamos por esto, y va primero porque…»

Escoges del backlog de Jira lo que entra a la semana, en orden. La razón importa más que el orden: sin cuenta de usuario no hay historial ni comentarios, así que la épica 1 va primera es una razón. Me parece más fácil no lo es.

02 «Esta historia está terminada cuando…»

Lees en voz alta los criterios de aceptación de cada tarjeta que entra. Si al leerlos en voz alta suenan ambiguos, se arreglan ahí mismo, en el Planning — no cuando ya esté programado. Un criterio ambiguo se convierte siempre en trabajo repetido.

03 «Esto no entra este sprint.»

Es la parte más incómoda y la más importante. Un sprint de una semana entre dos personas que además tienen otras cinco materias no aguanta cinco historias. Si dudas, saca una. Cerrar tres tarjetas prometidas vale más ante el comité que dejar cinco a medias.

Antes de cerrar la reunión

  • El sprint en Jira tiene fechas (martes → lunes) y está iniciado.
  • Toda tarjeta que entró tiene épica, componente (backend o frontend) y criterios de aceptación.
  • Quedó claro quién arranca cuál. Ambos programan backend y frontend — el docente lo exige y el reparto rota.
Miércoles a domingo

Sacar una tarjeta

El mismo circuito siempre, sin excepciones. Cinco pasos.

Todo se identifica por la key de la tarjeta de Jira: SCRUM-12, SCRUM-13. Esa key va en el nombre de la rama y también en cada commit. No es burocracia: es lo que hace que Jira muestre solo la rama, los commits y el PR pegados al issue, sin que nadie copie un link a mano. Un commit sin key queda huérfano y no aparece en el informe de sprint que se presenta al comité.

  1. Mueve la tarjeta a «In Progress» en Jira y copia su key

    Primero eso. Si no está en In Progress, para Santiago esa tarjeta está libre.

  2. Crea la rama, partiendo de main actualizado

    git switch main
git pull
git switch -c feature/SCRUM-12-registro-usuario

    El git pull no es opcional: si partes de un main viejo, después te toca resolver conflictos que no eran tuyos.

  3. Trabaja y commitea con la key

    git add .
git commit -m "feat(SCRUM-12): agregar formulario de registro"

    En español y empezando por el tipo: feat algo nuevo · fix un arreglo · docs documentación · test pruebas · refactor reacomodar sin cambiar comportamiento · chore el resto.

    Varios commits pequeños se leen mejor que uno gigante. Commitea cada vez que algo funcione.

  4. Sube la rama

    git push -u origin feature/SCRUM-12-registro-usuario

    El -u solo la primera vez de cada rama. Después basta git push.

  5. Abre el Pull Request en GitHub

    GitHub te muestra un botón amarillo «Compare & pull request» apenas subes. En el PR:

    • Título: la key y qué hace. SCRUM-12: registro de usuario
    • Descripción: qué cambia y cómo se prueba, en dos o tres líneas.
    • Reviewer: Santiago. Siempre.

    Y mueve la tarjeta a «In Review» en Jira.

La regla que no se rompe

Nadie mergea su propio PR. Ni tú el tuyo, ni Santiago el suyo. GitHub está configurado para rechazarlo, así que no depende de que a alguien se le olvide. Si un PR tuyo lleva días esperando, la solución es escribirle, no mergearlo.

Cuando te llegue un PR

Revisar backend sin saber Java

Tres preguntas que sí puedes responder sin leer el código línea por línea.

Vas a tener que aprobar PRs de Java antes de sentirte cómoda con Java. Eso está bien: una revisión útil no consiste en entender cada línea. Estas tres preguntas atrapan la mayoría de los problemas que importan, y las tres se contestan mirando la pestaña «Files changed» del PR.

01 ¿Está hecho lo que la tarjeta prometió?

Abre la tarjeta de Jira al lado y lee sus criterios de aceptación uno por uno. ¿Se ve en el diff algo que corresponda a cada uno? Si un criterio decía «la contraseña exige mínimo 8 caracteres, 1 mayúscula y 1 número» y no aparece nada parecido a una validación por ningún lado, esa es una observación perfectamente válida, aunque no sepas Java.

Esta pregunta es literalmente tu trabajo como PO. Nadie está mejor puesta que tú para hacerla.

02 ¿Se le coló una credencial?

En «Files changed» usa el buscador del navegador (Ctrl+F) sobre el diff y busca: password=, secret, api_key, apiKey, Bearer. Cualquier texto largo que parezca aleatorio es sospechoso.

Lo correcto se ve así, con la variable entre ${…}:

spring.datasource.password=${DB_PASSWORD}   bien
spring.datasource.password=Fusa2026*        bloquea el PR

Y si aparece un archivo llamado .env en la lista de archivos cambiados, ese solo hecho ya es motivo para no aprobar.

03 ¿Se contaminó domain/?

Es la única regla de arquitectura que tienes que vigilar, y se revisa mirando en qué carpeta está cada archivo, no qué dice.

Si un archivo del PR está dentro de src/main/java/com/fusaroute/domain/ y en sus primeras líneas aparece import org.springframework…, import jakarta.persistence… o @Entity, eso rompe la arquitectura hexagonal que le prometimos al docente. Coméntalo y no apruebes.

Por qué importa

domain/ son las reglas del negocio de FusaRoute —cómo se escoge la mejor ruta, cómo se calcula la tarifa— y tienen que poder existir sin Spring, sin base de datos y sin internet. Es lo que nos permite probarlas rápido y cambiar de base de datos sin reescribir nada. La explicación larga está en «Por qué trabajamos así».

Y de paso

  • ¿Los commits traen la key SCRUM-N?
  • ¿Aparecen carpetas que no deberían estar, tipo node_modules/, target/ o dist/?

Para aprobar: botón Review changes → Approve. Para pedir cambios, Request changes con un comentario concreto. Preguntar «¿esto qué hace?» es una revisión válida y útil — es exactamente el aprendizaje cruzado que el docente quiere ver.

Lunes · en la noche

Review, Retro e informe

Cierra el sprint. Es el documento que llega al comité, así que se escribe aunque la semana haya salido mal.

Primero Review: mostrar lo que quedó funcionando, corriéndolo de verdad, no contándolo. Después Retro: qué estorbó y qué se cambia la semana entrante. Y el informe se pega como comentario en el sprint cerrado de Jira.

Plantilla del informe

Sprint N · martes DD-mes → lunes DD-mes

Terminado. Las tarjetas que llegaron a Done, con su key. Solo las que están realmente en Done.

No terminado, y por qué. Lo que quedó abierto y la razón real. «Nos tomó más de lo estimado» es una razón; dejarlo en blanco no lo es.

Roles técnicos de este sprint. Quién respondió por frontend, por backend, por pruebas y por documentación. Rota cada dos sprints y hay que dejarlo escrito — es la evidencia de que ambos trabajamos todo el stack.

Participación. Commits y PRs revisados por cada uno. Sale de GitHub y el docente lo puede ver: git shortlog -sn tiene que devolver dos nombres.

Qué cambia la próxima semana. Una sola cosa concreta salida de la Retro. Una que se pueda cumplir, no cinco propósitos.

Cómo se escribe

Con los números reales. Un sprint donde se cerraron dos de cuatro tarjetas, contado tal cual y con la razón, se sustenta bien. Uno inflado se cae con una sola pregunta del docente, y ahí se pierde mucho más que las dos tarjetas.

Cuando se rompa

Se va a romper

Lo de abajo pasa siempre, y ninguna es culpa tuya.

«No se reconoce el comando» — mvn, java, psql, node

Cierra PowerShell y ábrelo otra vez. Windows solo se entera de los programas nuevos al abrir una terminal nueva. Si tras reabrir sigue igual, el instalador no lo dejó en el PATH: usa la ruta completa del programa, como en el paso 2.

El backend arranca y se cae de una, hablando de DataSource o Connection refused

No está encontrando PostgreSQL. Tres cosas en orden: que el servicio postgresql esté corriendo (búscalo en «Servicios» de Windows), que la base fusaroute_dev exista, y que hayas pegado la línea larga que carga el .env en esa misma ventana antes de mvn spring-boot:run.

Port 8080 already in use

Ya tienes un backend corriendo en otra ventana. Búscala y ciérrala con Ctrl+C.

El frontend no levanta o da errores raros de módulos

Borra e instala de nuevo. Es normal y no pierdes nada:

cd C:\dev\FusaRoute\FusaRoute-FRONTEND
Remove-Item -Recurse -Force node_modules
npm ci
Git dice rejected o non-fast-forward al hacer push

Alguien subió algo a esa rama después de que tú bajaste. Trae lo de arriba y vuelve a subir:

git pull --rebase
git push

Si aparecen conflictos, páralo ahí y escríbele a Santiago. Resolver un conflicto mal borra trabajo, y es de las poquísimas cosas en Git que sí duelen.

Metí la pata y quiero deshacer lo último

Mientras no hayas hecho push, casi todo es recuperable:

git status                  # siempre empieza por aquí
git restore <archivo>       # botar cambios de un archivo
git reset --soft HEAD~1     # deshacer el último commit, conservando el trabajo

Si ya hiciste push, no borres ni fuerces nada: avisa. Se arregla con otro commit, tranquilamente.
