Requisitos No Funcionales Calidad medible, no buena intención

🎯 Objetivo del slide: Defender los 7 RNFs con números realistas y justificar la eliminación del RNF-08.

Entrada "Siguiendo las exigencias del curso, ningún atributo de calidad se enuncia sin un criterio cuantitativo. Definimos 7 requisitos no funcionales:"

"• Eficiencia (RNF-01): tiempo de respuesta p95 menor a 5 segundos de extremo a extremo en red móvil 4G, con modo offline básico que muestra rutas y paradas almacenadas. • Fiabilidad (RNF-02): disponibilidad mayor o igual al 95% mensual en horario hábil (lun–vie 7 a 21 h), con RTO menor a 1 hora y RPO menor a 24 horas. • Mantenibilidad (RNF-03): arquitectura hexagonal estricta sin dependencias de frameworks en el dominio. • Usabilidad (RNF-04): búsqueda en 4 o menos acciones de usuario con login persistente semanal. • Seguridad (RNF-05 y 06): 0 vulnerabilidades altas/críticas y contraseñas hasheadas obligatoriamente con BCrypt factor 10. • Compatibilidad (RNF-07): navegadores móviles Chrome y Safari, más escritorio."

💡 Defensa RNF-08: Se eliminó porque el respaldo (`pg_dump`) es práctica de ingeniería, no RNF formal.
🔑 Modo offline: Aclarar que NO calcula tiempo de llegada sin internet (honesto).

Calidad y Métricas ISO 25010 Atributo + Métrica + Instrumento

🎯 Objetivo del slide: El slide más importante de evaluación: mostrar la correspondencia 1 a 1 entre atributo, métrica e instrumento ejecutable en CI.

Entrada "En la versión 3 aplicamos un principio inquebrantable: lo que no se puede medir en CI o con usuarios, no se promete. Establecimos 5 métricas, una por atributo ISO/IEC 25010:"

"1. Rendimiento: p95 < 5 s en `/api/routes/search` y LCP < 2.5 s. ➔ Instrumento: Spring Boot Actuator con Micrometer y Lighthouse en CI. 2. Fiabilidad: ≥ 95% uptime mensual hábil, RTO < 1 h. ➔ Instrumento: UptimeRobot con monitoreo cada 5 min y backup diario de PostgreSQL. 3. Mantenibilidad: 0 violaciones hexagonales y ≥ 70% cobertura en dominio. ➔ Instrumento: Reglas bloqueantes de ArchUnit y reporte de JaCoCo en CI. 4. Usabilidad: Flujo en ≤ 4 pasos con tasa de éxito ≥ 80%. ➔ Instrumento: Pruebas con al menos 5 usuarios externos antes de cada entrega. 5. Seguridad: 0 vulnerabilidades conocidas. ➔ Instrumento: OWASP Dependency-Check en cada Pull Request."

💡 Mención obligatoria: Citar los nombres de las herramientas: ArchUnit, JaCoCo, UptimeRobot, OWASP.
🔑 Defensa del 95%: Explicar que 95% es realista para capa gratuita (36 h/mes) vs el 99% que requiere pago.

Arquitectura Hexagonal Puertos y Adaptadores

🎯 Objetivo del slide: Explicar el desacoplamiento del backend, la regla de dependencia hacia adentro y el aislamiento de la base de datos.

Entrada "En la arquitectura técnica implementamos el patrón de Puertos y Adaptadores (Arquitectura Hexagonal) en el backend:"

"En el núcleo se encuentra el Dominio (`Route`, `Stop`, `Fare`), que contiene la lógica pura de transporte. El dominio no importa Spring Boot, no importa JPA y no conoce Supabase. La regla de dependencia apunta siempre hacia adentro: `domain ← application ← infrastructure`."

"Los Puertos de Entrada exponen los casos de uso a la API REST. Los Puertos de Salida definen las interfaces para que los adaptadores de infraestructura persistan en PostgreSQL o consuman Google Maps. El frontend en React solo habla con el backend mediante JSON y JWT; jamás toca la base de datos directamente."

💡 Concepto clave: 'Dos modelos a propósito': `Route` de dominio vs `RouteJpaEntity` de persistencia.
🔑 Beneficio: Cambiar de motor de base de datos no altera ni una sola línea del dominio.

Pregunta #1 · Criterio de Arquitectura
"¿Por qué decidieron usar Arquitectura Hexagonal en un proyecto pequeño en lugar de un MVC tradicional?"
Defensa recomendada (Angélica / Santiago):
"Aunque el proyecto inicie con 20 rutas, la premisa de la ingeniería de software es diseñar para crecer. Hexagonal nos permite aislar el modelo de transporte (`Route`, `Fare`) de cualquier tecnología externa. Si mañana cambiamos de Supabase a una base de datos propia, o si cambiamos la API de mapas por OpenStreetMap, el núcleo de negocio no sufre ningún cambio. Matriz de Métricas de Calidad (ISO/IEC 25010) — v3

Resumen de las 5 métricas oficiales aprobadas tras la revisión interna del 2026-08-24.

Atributo ISO 25010 Métrica Comprometida Instrumento de Medición en CI
Eficiencia de Desempeño p95 < 5 s en /api/routes/search + LCP < 2.5 s Spring Boot Actuator + Micrometer (percentil 95) y Lighthouse en CI sobre red móvil Slow 4G.
Fiabilidad (Disponibilidad) ≥ 95% mensual en horario hábil (7-21h), RTO < 1 h, RPO < 24 h UptimeRobot (sonda cada 5 min) + backup diario de PostgreSQL con prueba de restore al cierre de sprint.
Mantenibilidad 0 violaciones hexagonales en CI + ≥ 70% cobertura en domain/ ArchUnit sobre los paquetes del backend + reporte JaCoCo con umbral bloqueante en PR.
Usabilidad Flujo ≤ 4 acciones + tasa de éxito ≥ 80% al 1er intento Prueba de usabilidad con ≥ 5 usuarios externos al equipo antes de cada sustentación quincenal.
Seguridad 0 vulnerabilidades altas o críticas en la entrega OWASP Dependency-Check + analizador estático en GitHub Actions en cada Pull Request.

Reglas de la Arquitectura Hexagonal

  • Dirección: domain ← application ← infrastructure.
  • Dominio: Cero imports de org.springframework.*, javax.persistence.* o librerías HTTP.
  • Puertos: Interfaces en domain/port/in y domain/port/out.
  • Adaptadores: Web controllers en in/web, repositorios JPA en out/persistence.

Decisiones Clave del Stack

  • PostgreSQL en Supabase: Usado exclusivamente como motor de BD relacional (sin Auth ni Realtime).
  • Seguridad: Spring Security + JWT propio con BCrypt (factor ≥ 10).
  • Google Maps API: Solo para geocodificación y tiempos estimados; nunca como fuente de rutas de busetas.
  • Git: PRs cruzados obligatorios (ninguno aprueba su propio PR).
